 1. iot_agent/llm.py のプロンプト構築とパース処理 (最も推奨)
  現在、_structured_llm_promptでシステムプロンプトにデバイス一覧（コンテキスト）を埋め込み、_call_llm_and_parseでLLMの出力を正規表現やJSONデコーダで無理やり解析しています。
これを MCP Server化 することで、以下のメリットがあります。
* Tool定義の標準化: device_commands のJSONスキーマを独自にメンテナンスする代わりに、MCPの CallToolインターフェースを利用できます。
 * コンテキストの動的管理: _build_device_context で毎回全デバイス情報をプロンプトに含めるのではなく、MCPの Resourcesとして定義し、LLMが必要なときだけ（または重要なデバイスだけ）を読みに行かせる形にできます（トークン節約 ）。
 * パース処理の廃止: LLM側（ClaudeやOpenAIのFunctionCalling対応クライアント）がMCPプロトコルに従ってツールを呼ぶため、脆弱な try-exceptブロックや「JSONだけ返して」という指示が不要になります。

  2. 外部エージェントとの連携 (/api/conversations/review 周り)
  現在、他のエージェントから会話ログを受け取って解析していますが、このIoTサーバー自体をMCP Server として公開。


 3. 登録されているデバイス情報を、オーケストレーターに渡す処理をMCP化。


  結論:
  まずは Flaskサーバー自体を MCP Server 化 し、llm.py 内の独自プロンプト・パース処理を MCP の Tool/Resourceシステムに置き換えるのが最も効果的です。
